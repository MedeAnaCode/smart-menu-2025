Техническое задание на развитие приложения SmartMenu
1. Пользовательские сценарии
   1.1. Авторизация
   Пользователь может:
   зарегистрироваться;
   войти в приложение;
   выйти из приложения;
   восстановить пользовательскую сессию после перезагрузки страницы.
   После авторизации пользователь получает доступ:
   к своим недельным меню;
   к собственной коллекции рецептов;
   к собственным спискам покупок;
   к общему каталогу опубликованных рецептов.
   Личные данные одного пользователя не должны быть доступны другим пользователям.
   Ограничения доступа должны обеспечиваться на стороне backend, а не только путём скрытия элементов интерфейса.

1.2. Работа с рецептами
1.2.1. Общий каталог рецептов
Пользователь может:
просматривать общий каталог опубликованных рецептов;
искать рецепты по названию;
открывать карточку рецепта;
добавлять рецепт в коллекцию «Мои рецепты»;
использовать опубликованный рецепт при составлении меню.
1.2.2. Раздел «Мои рецепты»
В разделе отображаются:
рецепты, созданные текущим пользователем;
рецепты, сохранённые пользователем из общего каталога.
Пользователь может:
создать собственный рецепт;
открыть рецепт;
редактировать собственный рецепт;
удалить собственный рецепт;
удалить сохранённый рецепт из своей коллекции;
создать собственный рецепт на основе сохранённого рецепта;
использовать рецепт при составлении меню.
Пользователь не может редактировать рецепт другого автора.

1.3. Создание и редактирование рецепта
При создании или редактировании собственного рецепта пользователь может указать:
название;
описание;
базовое количество порций;
категорию;
список ингредиентов;
количество и единицу измерения каждого ингредиента;
этапы приготовления;
изображение.
Изображение должно загружаться через интерфейс и сохраняться таким образом, чтобы оно не терялось после перезапуска приложения.
Не следует хранить изображение в виде base64 в основной таблице рецептов.
Конкретный способ хранения необходимо выбрать с учётом текущей инфраструктуры проекта. Для локальной разработки допускается файловое хранилище с Docker volume. В базе данных должна храниться ссылка или путь к файлу.

1.4. Публикация рецептов
Созданный рецепт по умолчанию является личным и доступен только его автору.
Автор может опубликовать собственный рецепт.
После публикации рецепт:
становится доступен в общем каталоге;
сохраняет информацию об авторе;
может быть добавлен другими пользователями в их коллекции;
может использоваться другими пользователями при составлении меню;
не может редактироваться другими пользователями.
Автор может снять рецепт с публикации.
После снятия с публикации рецепт:
исчезает из общего каталога;
удаляется из коллекций других пользователей;
остаётся доступен автору;
не должен повреждать ранее созданные меню, в которые он был добавлен.
Добавление рецепта из общего каталога в «Мои рецепты» создаёт связь между пользователем и существующим рецептом, а не отдельную копию.
Сохранённый рецепт нельзя редактировать. Пользователь может:
удалить его из своей коллекции;
создать на его основе новый собственный рецепт.

1.5. Отображение рецепта и изменение количества порций
У каждого рецепта есть базовое количество порций.
На странице рецепта пользователь может выбрать другое количество порций.
При изменении количества порций:
количество всех ингредиентов должно автоматически пересчитываться;
пользователь должен видеть количества ингредиентов, рассчитанные для выбранного числа порций;
исходные данные рецепта не должны изменяться;
выбранное при просмотре количество порций не должно сохраняться в самом рецепте.
При добавлении рецепта в меню выбранное количество порций сохраняется в соответствующей позиции меню независимо от базового количества порций рецепта.

1.6. Планирование меню
Пользователь может создавать и хранить несколько недельных меню.
Каждое меню состоит из дней.
Каждый день может содержать:
завтрак;
обед;
ужин;
дополнительные или пользовательские приёмы пищи.
Каждый приём пищи может содержать:
один или несколько рецептов;
дополнительные продукты, не оформленные как рецепт.
Для каждого добавленного рецепта пользователь задаёт количество порций.
Пользователь может:
добавлять рецепты;
удалять рецепты;
изменять количество порций;
добавлять дополнительные продукты;
удалять дополнительные продукты;
очищать отдельный приём пищи;
очищать целый день.
Дополнительные продукты
Для дополнительного продукта хранятся:
название;
количество;
единица измерения;
признак участия в расчёте списка покупок.
На текущем этапе дополнительные продукты:
не сопоставляются автоматически с общей базой ингредиентов;
не объединяются с другими дополнительными продуктами;
переносятся в список покупок отдельными позициями.

1.7. Выбор позиций для расчёта списка покупок
По умолчанию все позиции меню участвуют в расчёте списка покупок.
Пользователь может исключить из расчёта:
отдельный рецепт;
отдельный дополнительный продукт;
весь приём пищи;
весь день.
Исключённые позиции не должны учитываться при следующем расчёте списка покупок.

1.8. Расчёт списка покупок
Пользователь может сформировать список покупок на основании выбранного недельного меню.
У каждого недельного меню существует один актуальный список покупок.
При расчёте система должна:
учитывать только включённые в расчёт дни, приёмы пищи и позиции;
получать ингредиенты добавленных рецептов;
пересчитывать количество ингредиентов с учётом выбранного количества порций;
объединять одинаковые ингредиенты из общей базы при совпадении единиц измерения;
суммировать их количество;
добавлять кастомные ингредиенты отдельными строками;
добавлять дополнительные продукты отдельными строками;
сохранять сформированный список покупок.
Повторный расчёт заменяет актуальный список покупок новым.

1.9. Работа со списком покупок
После расчёта пользователь может:
удалить позицию;
добавить новую позицию вручную;
изменить название позиции;
изменить количество;
изменить единицу измерения;
отметить продукт как купленный;
снять отметку «Куплено».
Повторный расчёт списка покупок:
удаляет текущий рассчитанный список;
удаляет добавленные вручную позиции;
сбрасывает ручные изменения;
формирует новый список по актуальному состоянию меню.
Перед повторным расчётом пользователь должен получить предупреждение о потере ручных изменений.
Подтверждение необходимо запрашивать только в том случае, если пользователь действительно внёс ручные изменения.

1.10. Общая база ингредиентов
Все рецепты используют единую общую базу ингредиентов.
Одинаковые ингредиенты должны ссылаться на одну и ту же сущность базы данных. Это необходимо для их корректного объединения при формировании списка покупок.
При добавлении ингредиента в рецепт пользователь может:
выбрать ингредиент из общей базы;
добавить кастомный ингредиент вручную, если подходящего варианта нет.
Ингредиент из общей базы хранит ссылку на соответствующую запись базы ингредиентов.
Кастомные ингредиенты
Кастомный ингредиент хранит:
введённое пользователем название;
количество;
единицу измерения.
Кастомный ингредиент:
принадлежит конкретному рецепту;
не добавляется автоматически в общую базу;
не участвует в поиске по общей базе;
не объединяется с ингредиентами из общей базы;
не объединяется автоматически с другими кастомными ингредиентами;
добавляется в список покупок без изменения названия;
сохраняет указанное пользователем количество и единицу измерения.
В интерфейсе кастомные ингредиенты должны визуально отличаться от ингредиентов общей базы.
Для этого следует использовать неброскую цветовую метку или подпись «Свой ингредиент».
Рядом с возможностью добавить кастомный ингредиент необходимо показать пояснение о том, что такие позиции не объединяются при расчёте списка покупок.

1.11. Пользовательские и общие данные
У каждого пользователя независимо хранятся:
собственные рецепты;
коллекция сохранённых рецептов;
недельные меню;
списки покупок.
Общими для всех пользователей являются:
каталог опубликованных рецептов;
база ингредиентов.
Все рецепты физически могут храниться в единой базе данных, но должны иметь уровень видимости:
private — рецепт доступен только автору;
published — рецепт доступен в общем каталоге.
Наличие рецепта в общей таблице базы данных не означает его доступность другим пользователям.

2. Технологический стек
   Указанный стек является целевым.
   Если часть перечисленных библиотек ещё не используется, её необходимо внедрить для соответствующих задач.
   2.1. Frontend
   React;
   TypeScript;
   React Router;
   Redux Toolkit;
   RTK Query;
   React Hook Form;
   Zod.
   Рекомендуемое назначение библиотек:
   React Hook Form и Zod — формы и валидация;
   Redux Toolkit — клиентское состояние, которое используется в нескольких частях приложения;
   RTK Query — работа с серверными данными и API;
   React Router — маршрутизация.
   Не следует переносить в глобальное состояние данные, которые используются только внутри одного локального компонента.
   2.2. Backend
   Node.js;
   Express;
   Sequelize;
   PostgreSQL;
   Zod;
   Keycloak.
   Keycloak используется для:
   регистрации;
   входа;
   выхода;
   управления пользовательской сессией;
   определения текущего пользователя.
   2.3. Infrastructure
   Docker;
   Git.
   2.4. Тестирование
   Playwright — end-to-end-тестирование пользовательских сценариев;
   существующий unit-test runner проекта — тестирование бизнес-логики.
   Если unit-test runner в проекте отсутствует, необходимо выбрать инструмент, совместимый с текущей конфигурацией проекта.

3. Границы текущего этапа
   На текущем этапе необходимо доработать существующий проект до рабочего состояния, поддерживающего пользовательские сценарии, описанные в разделе 1.
   Не следует:
   добавлять функциональность, не описанную в требованиях;
   проводить полный редизайн приложения;
   изменять выбранный технологический стек без объективной необходимости;
   переписывать работающие части проекта, если их можно последовательно доработать;
   выполнять оптимизации, которые не требуются для реализации описанных сценариев.
   Если весь объём невозможно надёжно реализовать за один проход, необходимо:
   определить, какие требования уже реализованы полностью или частично;
   составить краткий план работ;
   определить зависимости между функциями;
   разделить работу на последовательные этапы;
   после каждого этапа сохранять проект в рабочем состоянии.

4. Дизайн и пользовательский интерфейс
   Необходимо провести UX/UI-аудит существующего интерфейса.
   Общую визуальную концепцию и цветовое решение приложения необходимо сохранить.
   Допускается улучшать:
   композицию экранов;
   визуальную иерархию;
   размеры элементов;
   систему отступов;
   типографику;
   формы;
   состояния компонентов;
   понятность пользовательских действий;
   отображение загрузки, ошибок и пустых состояний.
   Формы создания и редактирования необходимо переработать, если их текущее устройство затрудняет использование приложения.
   При разработке новых экранов и компонентов необходимо придерживаться существующих:
   цветовой палитры;
   типографики;
   отступов;
   компонентов;
   иконок;
   принципов оформления;
   общего визуального стиля.
   Новый компонент должен выглядеть так, как будто он изначально являлся частью проекта.
   Следует предпочитать эволюционные улучшения революционным изменениям.

5. Работа с существующим проектом
   Проект уже содержит частично реализованные:
   frontend;
   backend;
   пользовательский интерфейс;
   отдельные пользовательские сценарии.
   Существующая реализация должна использоваться как основа проекта.
   Необходимо определить:
   какие требования уже выполнены;
   какие требования реализованы частично;
   какие требования отсутствуют;
   какие существующие решения требуют адаптации под целевой стек.
   Библиотеки, указанные в разделе 2, должны быть внедрены там, где соответствующая задача:
   ещё не реализована;
   реализована несовместимым способом;
   требует модернизации для выполнения настоящего ТЗ.
   Переход должен выполняться последовательно, без необоснованного полного переписывания проекта.

6. Модель данных и бизнес-правила
   Названия сущностей и точная схема базы данных могут быть адаптированы к существующей архитектуре проекта. При этом описанные связи и бизнес-ограничения должны сохраняться.
   6.1. Основные сущности
   Предполагаемый набор основных сущностей:
   User — пользователь приложения, связанный с пользователем Keycloak;
   Recipe — рецепт, его автор, видимость и базовое количество порций;
   Ingredient — элемент общей базы ингредиентов;
   RecipeIngredient — ингредиент конкретного рецепта;
   SavedRecipe — связь пользователя с сохранённым опубликованным рецептом;
   Menu — недельное меню пользователя;
   MenuDay — день меню;
   Meal — приём пищи;
   MealRecipe — рецепт внутри приёма пищи;
   MealProduct — дополнительный продукт внутри приёма пищи;
   ShoppingList — актуальный список покупок конкретного меню;
   ShoppingListItem — позиция списка покупок.
   Не обязательно создавать отдельную таблицу для каждой перечисленной сущности, если существующая архитектура позволяет сохранить те же связи и ограничения более простым способом.

6.2. Пользователь
Пользователь может изменять только принадлежащие ему данные:
собственные рецепты;
собственные меню;
собственные списки покупок;
собственную коллекцию сохранённых рецептов.
Идентификатор пользователя должен быть связан с учётной записью Keycloak.

6.3. Рецепт
Рецепт должен содержать:
автора;
уровень видимости;
название;
описание;
базовое количество порций;
категорию;
изображение;
этапы приготовления;
список ингредиентов.
Личный рецепт доступен только автору.
Опубликованный рецепт доступен в общем каталоге, но изменять его может только автор.

6.4. Сохранённый рецепт
Добавление опубликованного рецепта в раздел «Мои рецепты» создаёт связь между пользователем и оригинальным рецептом.
Отдельная копия рецепта при сохранении не создаётся.
Сохранённый рецепт:
нельзя редактировать;
можно удалить из коллекции;
можно использовать при составлении меню;
можно использовать как основу для создания нового собственного рецепта.

6.5. Ингредиенты рецепта
Каждая позиция ингредиента в рецепте может быть:
ссылкой на ингредиент из общей базы;
кастомным ингредиентом.
Для одной позиции должен использоваться только один из этих вариантов.
Позиция ингредиента должна содержать:
количество;
единицу измерения;
ссылку на общий ингредиент либо название кастомного ингредиента.

6.6. Количество порций
У рецепта существует базовое количество порций.
Количество ингредиента для выбранного числа порций рассчитывается пропорционально:
итоговое количество =
базовое количество ингредиента × выбранное количество порций / базовое количество порций рецепта

Изменение числа порций:
не изменяет оригинальный рецепт;
влияет на отображаемое количество ингредиентов;
учитывается при формировании списка покупок;
сохраняется в позиции меню.

6.7. Меню
Меню принадлежит одному пользователю и состоит из дней и приёмов пищи.
Позиция рецепта внутри меню должна хранить:
ссылку на рецепт;
выбранное количество порций;
признак участия в расчёте списка покупок;
данные, необходимые для сохранения работоспособности меню после снятия рецепта с публикации.
Дополнительный продукт внутри меню должен хранить:
название;
количество;
единицу измерения;
признак участия в расчёте.

6.8. Список покупок
У каждого меню существует один актуальный список покупок.
Позиция списка покупок должна поддерживать:
название;
количество;
единицу измерения;
источник позиции;
ручное редактирование;
отметку «Куплено».
Источником позиции может быть:
общий ингредиент рецепта;
кастомный ингредиент рецепта;
дополнительный продукт меню;
вручную добавленный продукт.

6.9. Единицы измерения
На текущем этапе автоматическое преобразование единиц измерения не реализуется.
Ингредиенты объединяются только при одновременном совпадении:
идентификатора общего ингредиента;
единицы измерения.
Например:
две позиции одного ингредиента в граммах объединяются;
позиции одного ингредиента в граммах и килограммах остаются отдельными строками.
Кастомные ингредиенты и дополнительные продукты автоматически не объединяются.

7. Требования к архитектуре
   7.1. Общие требования
   При разработке необходимо:
   сохранять существующую архитектуру там, где она не препятствует реализации требований;
   использовать целевые библиотеки, указанные в разделе 2;
   разделять UI, бизнес-логику и работу с данными;
   выносить вычисления и бизнес-правила из React-компонентов;
   сохранять строгую типизацию;
   централизовать работу с API;
   не создавать избыточные абстракции;
   не дублировать одни и те же бизнес-правила в разных частях проекта.

7.2. Работа с API и серверными данными
Для работы с серверными данными следует использовать единообразный подход на основе RTK Query.
Необходимо:
централизованно описывать API-запросы;
корректно обрабатывать состояния загрузки;
отображать ошибки;
обновлять связанные серверные данные после изменений;
не считать данные сохранёнными до получения успешного ответа backend;
не дублировать одинаковые запросы в разных компонентах.

7.3. Формы и валидация
Для форм следует использовать React Hook Form и Zod.
Валидация должна выполняться:
на frontend — для быстрой обратной связи пользователю;
на backend — для обеспечения целостности и безопасности данных.
Формы должны поддерживать:
понятные подписи полей;
сообщения об ошибках;
сохранение введённых данных при ошибке отправки;
блокировку повторной отправки;
состояние загрузки;
подтверждение успешного сохранения.

7.4. Бизнес-логика
Расчёт списка покупок необходимо вынести в отдельный модуль или сервис.
Расчётная логика не должна зависеть:
от DOM;
от React-компонентов;
от конкретного способа визуального отображения результата.
Отдельно должны обрабатываться:
пересчёт ингредиентов по количеству порций;
исключение отключённых позиций;
объединение общих ингредиентов;
разделение позиций с разными единицами;
обработка кастомных ингредиентов;
обработка дополнительных продуктов;
повторное формирование списка покупок.

7.5. Тестирование
Unit-тесты
Unit-тестами необходимо покрыть критичную бизнес-логику:
пересчёт ингредиентов по количеству порций;
объединение одинаковых общих ингредиентов;
отсутствие объединения ингредиентов с разными единицами;
исключение отключённых позиций;
обработку кастомных ингредиентов;
обработку дополнительных продуктов.
End-to-end-тесты
Для проверки пользовательских сценариев необходимо использовать Playwright.
Минимально покрыть следующие сценарии:
регистрация или вход пользователя;
восстановление пользовательской сессии;
создание рецепта;
редактирование собственного рецепта;
публикация и снятие рецепта с публикации;
сохранение опубликованного рецепта в коллекцию;
изменение отображаемого количества порций;
добавление рецепта в меню;
добавление дополнительного продукта;
исключение позиции из расчёта;
формирование списка покупок;
ручное изменение списка покупок;
повторный расчёт и подтверждение сброса ручных изменений.

8. Критерии готовности
   Работа считается завершённой, если выполнены все обязательные требования настоящего ТЗ.
   8.1. Общая работоспособность
   Проект успешно устанавливается и запускается.
   Проект успешно собирается.
   Отсутствуют новые ошибки TypeScript.
   Отсутствуют новые ошибки линтера.
   Основные пользовательские сценарии не вызывают необработанных ошибок.
   Существующая рабочая функциональность не сломана.
   Инструкция по запуску проекта актуальна.
   8.2. Авторизация и доступ
   Пользователь может зарегистрироваться.
   Пользователь может войти и выйти.
   Сессия восстанавливается после перезагрузки страницы.
   Личные данные пользователя недоступны другим пользователям.
   Ограничения доступа обеспечиваются backend.
   8.3. Рецепты
   Пользователь может создавать, открывать, редактировать и удалять собственные рецепты.
   Рецепт поддерживает общие и кастомные ингредиенты.
   Пользователь может загрузить изображение рецепта.
   Изображение сохраняется после перезапуска приложения.
   Пользователь может опубликовать рецепт и снять его с публикации.
   Опубликованный рецепт появляется в общем каталоге.
   Другой пользователь не может изменить опубликованный рецепт.
   Пользователь может сохранить опубликованный рецепт в свою коллекцию.
   Сохранённый рецепт не копируется и не может редактироваться.
   Количество ингредиентов корректно пересчитывается при изменении числа порций.
   8.4. Меню
   Пользователь может создавать и хранить несколько недельных меню.
   Меню содержит дни и приёмы пищи.
   В приём пищи можно добавить несколько рецептов.
   Для рецепта можно изменить количество порций.
   В меню можно добавить дополнительный продукт.
   Пользователь может удалить рецепт или продукт.
   Пользователь может очистить приём пищи или день.
   Пользователь может исключить из расчёта отдельную позицию, приём пищи или день.
   Меню сохраняется после обновления страницы.
   Снятие использованного рецепта с публикации не повреждает меню.
   8.5. Список покупок
   У каждого меню есть один актуальный список покупок.
   Список корректно рассчитывается по выбранным позициям меню.
   Количество ингредиентов учитывает выбранное количество порций.
   Общие ингредиенты объединяются только при совпадении единиц измерения.
   Кастомные ингредиенты не объединяются автоматически.
   Дополнительные продукты не объединяются автоматически.
   Исключённые позиции не участвуют в расчёте.
   Пользователь может добавлять, изменять и удалять позиции вручную.
   Пользователь может отмечать продукты как купленные.
   Повторный расчёт заменяет текущий список.
   Перед потерей ручных изменений отображается предупреждение.
   8.6. Интерфейс
   Интерфейс соответствует существующей визуальной концепции.
   Новые экраны и компоненты визуально согласованы с существующими.
   Формы имеют понятную структуру и валидацию.
   Реализованы состояния загрузки, ошибки и пустых данных.
   Основные действия имеют понятную визуальную обратную связь.
   Кастомные ингредиенты визуально отличаются от общих.
   8.7. Тестирование
   Критичная бизнес-логика покрыта unit-тестами.
   Основные пользовательские сценарии покрыты Playwright-тестами.
   Добавленные тесты проходят успешно.

9. Правила изменения существующего кода
   Не переписывать рабочий код без технической необходимости.
   Предпочитать последовательную модернизацию существующей реализации.
   Использовать целевые библиотеки, указанные в настоящем ТЗ.
   Не изменять технологический стек без объективной причины.
   Не обновлять зависимости, если это не требуется для реализации функциональности.
   Не смешивать масштабный рефакторинг с добавлением новой функциональности, если эти изменения можно разделить.
   После каждого значимого изменения сохранять проект в рабочем состоянии.
   Использовать строгую типизацию.
   Не отключать проверки TypeScript, линтер или тесты ради прохождения сборки.
   Не использовать any без крайней необходимости.
   Переиспользовать существующие компоненты и стили.
   Не изменять общую визуальную концепцию приложения.
   Не добавлять новые абстракции без реальной необходимости.
   Не дублировать существующие компоненты, бизнес-правила и API-запросы.
   Не хранить секреты, пароли и токены в исходном коде.
   При изменении базы данных создавать корректные миграции.
   Не редактировать старые применённые миграции вместо создания новых.
   Если обнаружена архитектурная проблема, не связанная напрямую с текущей задачей:
   зафиксировать проблему;
   не выполнять масштабный рефакторинг без необходимости;
   исправить только ту часть, которая блокирует реализацию.
   После завершения работы запустить доступные проверки и тесты.
   По завершении предоставить краткий отчёт, содержащий:
   перечень реализованной функциональности;
   список основных изменённых файлов;
   результаты проверок и тестов;
   известные ограничения;
   функциональность, которую не удалось завершить, и причины.
