# Названия ингредиентов

Стандарт справочника и поля `name` при AI-импорте: именительный падеж, единственное число независимо от количества, первая буква заглавная. Например: `Яйцо`, `Огурец`, `Помидор`, `Томат`, `Гриб`, `Креветка`, `Маслина`, `Лист лайма`. Буква ё пишется по орфографии: `Мёд`, `Сушёный розмарин`, `Чёрный перец`; сопоставление не заменяет е на ё автоматически.

Обычные согласованные прилагательные ставим перед существительным: `Оливковое масло`, `Кокосовое молоко`, `Куриное филе`, `Лимонный сок`, `Сушёный розмарин`. Родительные конструкции и именованные продукты сохраняем: `Зубчик чеснока`, `Лист лайма`, `Сыр Фета`, `Соус Терияки`.

Назначение «для жарки», «для украшения» и другие инструкции использования остаются в предупреждениях, а не в каноническом имени продукта.

Сохраняем естественные множественные названия: `Спагетти`, `Макароны`, `Сливки`, `Овсяные хлопья долгой варки`. Значимые уточнения и части продукта сохраняются. Правило касается названий ингредиентов, а не текста описания или приготовления.

Сопоставление с общей базой — точное после удаления крайних пробелов и приведения к нижнему регистру (`toLocaleLowerCase("ru-RU")`). При совпадении форма использует ID и отображаемое название из базы; количество и единица сохраняются. `Яйцо`, `яйцо` и `ЯЙЦО` совпадают. Несовпавший ингредиент остаётся своим.

В этом варианте нет словаря синонимов, морфологии или выбора ID моделью. `Помидор` и `Томат` остаются разными записями. Если LLM нарушит инструкцию и вернёт `Яйца`, сервер не превращает это слово в `Яйцо` автоматически. Обновление seed задаёт названия для новых баз; существующий справочник требует отдельной миграции с сохранением связей.

## Обновление существующего справочника

Миграция `docs/migrations/2026-09-22-canonical-ingredient-names.sql` переименовывает известные записи на месте и обновляет `normalizedName`. ID и внешние ключи ингредиентов рецептов сохраняются. Она запускается стандартным механизмом миграций backend в транзакции. При конфликте с уже существующим каноническим названием транзакция прерывается: дубли нужно разрешить отдельно, автоматического объединения ID нет. Исторические снимки рецептов, меню и покупок, а также собственные ингредиенты остаются неизменными.

Рабочая ветка `codex/recipe-api-canonical-ingredients` находится в `C:/Users/Anastakisa/.codex/worktrees/recipe-api-canonical/Smart-menu_React`. Из папки новой копии можно поднять отдельный стек:

```powershell
docker compose --project-name smartmenu-api-canonical -f docker-compose.yml -f docker-compose.e2e.yml up -d --build
```

Отдельное имя проекта создаёт отдельные Docker volumes. Override задаёт порты `9100` для приложения, `3101` для backend, `8180` для Keycloak и `5433` для PostgreSQL. Они должны быть свободны, в том числе от другого e2e-стека. Такой запуск не использует базу и контейнеры исходного проекта; миграция применяется к базе новой копии.

Открывайте приложение по адресу `http://127.0.0.1:9100`: этот адрес разрешён в redirect URI Keycloak для изолированного стека.
